This is a solid production foundation, but I’d fix several security and data-integrity gaps before calling it production-ready. The architecture is appropriately simple, and the deployment work is substantial.
What’s already good: non-root, multi-stage containers; persistent Data Protection keys; migrations gated before deployment; OpenTelemetry; separate liveness/readiness endpoints; validation; login lockouts; bounded fixture queries; and sensible static-file caching.
The main findings, in priority order:
	1. High — Google login bypasses the app’s two-factor authentication.
The callback explicitly uses bypassTwoFactor: true. It also automatically links an existing account by email and then calls SignInAsync, which skips that account’s TOTP challenge. Google authentication does not establish that the user completed your app’s second factor. Require the configured second factor, including when linking an existing account during login. 	2. High — A partial scrape can permanently delete valid fixtures and bookmarks.
Rejecting an empty result is useful, but a page containing just one successfully parsed fixture still passes. The sync then deletes every missing upcoming fixture from that source, with bookmarks deleted by cascade. Restrict deletion to a verified coverage window, reject suspicious reductions or parsing failures, and make reconciliation transactional. 	3. High — Rescheduling a match loses the user’s bookmark.
The provider’s external ID includes the match date. Moving a fixture to another day creates a new database fixture and deletes the original, including its bookmarks. Its calendar UID also changes. A scheduling app needs stable match identity across date changes, or explicit reconciliation that preserves references. 	4. High, infrastructure-dependent — Forwarded headers trust every proxy.
Both trusted-proxy lists are cleared while forwarded IP, host, and scheme are accepted. If ingress allows attacker-controlled values through, this can undermine IP rate limiting and influence authentication redirect URLs. Configure the actual proxy trust boundary and allowed hosts, and verify ingress overwrites those headers. 	5. Medium — Sensitive account operations need fresh authentication.
Disabling 2FA, generating replacement recovery codes, and deleting an account require only an existing session. A stolen or unattended session can therefore remove protection or destroy the account. Require a recent password, TOTP, or provider reauthentication for these actions. I found no automated test projects or client tests. CI runs on pushes, with no pull_request trigger.
